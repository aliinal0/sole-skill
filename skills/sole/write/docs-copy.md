# Docs and copy - READMEs, UI text, emails, posts

## Universal rules

- Write for the reader's task, in their words. Name things by what the user understands, not how the system is built ("notifications", not "webhook config").
- Lead with the point. One idea per sentence, one job per element.
- Active voice, plain verbs, sentence case. Specific nouns and numbers over adjectives.
- Cut every sentence that would not be missed.
- Finish with `write/humanize-text.md` checks.

## UI microcopy

- Buttons say what happens: "Save changes", "Send invoice". The same action keeps the same name through the flow ("Publish" -> "Published").
- Errors: what went wrong + how to fix it. No apologies, no vagueness, no blame.
- Empty states: what this place is for + the first action.
- Labels above fields, never placeholder-only.

## README

1. One line that names what it is and who it is for: "A command-line tool for analysts who clean CSV exports before importing them." A line that only says what it does is not enough.
2. A "Quick start" section that works when copied: install, run, first result.
3. Usage examples for the 2-3 main cases.
4. Configuration, then deeper docs links.
5. Contributing, license.
No marketing adjectives, no emoji walls, no "🚀 Features" headings by reflex.

## Emails and messages

Subject = the ask or the news. First line = what you need from the reader and by when. Context after. Sign-off short. Match the user's own voice if a sample exists (CONTEXT.md preferences).

## Posts (LinkedIn, X, blog)

Hook with a concrete observation, not a platitude. One story or data point. One takeaway. No "Here's why 🧵", no listicle of generic tips, no fake vulnerability.
